# Internacionalização (i18n)

O Oficio vem em inglês (`en`) e português do Brasil (`pt-BR`). Cada pessoa escolhe o próprio idioma, a instância tem um padrão para os recém-chegados, e os textos do lado do servidor (erros da API, e-mails, os rótulos do mapa padrão) seguem as mesmas regras. Esta página explica como o idioma é escolhido para os usuários, como os dicionários são organizados no código, como o servidor decide o idioma de uma resposta ou de um e-mail, e os passos exatos para adicionar um novo idioma.

## Para usuários e operadores

### Onde o idioma é escolhido

| Lugar | O que faz |
|---|---|
| **Página de login** (seletor na parte de baixo) | Troca a página de login imediatamente e guarda a escolha no navegador (`localStorage`, chave `oficio:locale`). A primeira opção, *auto*, significa "seguir o navegador". |
| **Configurações** no escritório (o menu de engrenagem, *Idioma*) | O mesmo seletor; adicionalmente salva a escolha no perfil do usuário (`PUT /api/me/settings`, campo `locale`), para que os e-mails enviados a essa pessoa a usem e a escolha a acompanhe em outro navegador. |
| **`OFFICE_DEFAULT_LOCALE`** no `.env` | Padrão da instância para quem não escolheu e cujo idioma do navegador não é suportado, e para mensagens do servidor quando uma requisição não diz nada sobre idioma. |

A interface inteira é redesenhada no lugar quando o idioma muda; sem recarregar.

### Ordem de resolução no navegador

1. A **escolha explícita** da pessoa (configuração do perfil, ou a escolha guardada no navegador antes do login).
2. Os **idiomas do navegador** (`navigator.languages`), casados primeiro exatamente (`pt-BR`), depois pelo idioma base (`pt-PT` → `pt-BR`, `en-GB` → `en`).
3. **`OFFICE_DEFAULT_LOCALE`**, lido de `GET /api/config`.
4. Se até isso for inválido: `en`.

`<html lang>` é mantido em sincronia para que leitores de tela e corretores ortográficos acompanhem.

### Como o servidor escolhe um idioma

O servidor atende muitas pessoas ao mesmo tempo, então resolve um locale **por requisição**:

1. `?lang=<locale>` na URL. Os links dos e-mails o carregam (`/login?reset=…&lang=pt-BR`) para que a página de login abra no idioma do destinatário antes de qualquer JavaScript rodar.
2. O header `Accept-Language`, ponderado por `q`, casado como acima.
3. `OFFICE_DEFAULT_LOCALE`.

Isso decide o idioma das mensagens de erro da API (`{"error": "…"}`), das recusas em texto puro do guard (`Host not allowed…`), da página `403` de administração, da mensagem de "client not built" e das mensagens de validação de mapa devolvidas ao editor. Para conexões WebSocket a mesma resolução roda no momento do upgrade, com o idioma salvo no perfil do usuário tendo precedência.

**E-mails** usam o idioma salvo do destinatário quando a conta tem um (redefinições de senha, redefinições feitas por administradores); convites para contas recém-criadas, que ainda não têm idioma salvo, usam o idioma da requisição do administrador. Assunto, corpo e rótulos dos botões vêm das chaves `server.mail.*`.

**O mapa padrão** é gerado com rótulos em um idioma concreto: na primeira inicialização, os nomes das salas e as placas são escritos em `OFFICE_DEFAULT_LOCALE` e armazenados como dados no mapa publicado. Alterar o locale padrão depois não renomeia as salas; edite-as no editor de mapa ou use *Restaurar mapa padrão* no editor para regenerar o rascunho no idioma padrão atual. A placa da marca usa o rótulo neutro `{brand}`.

### Locales suportados

| Código | Nome mostrado nos seletores |
|---|---|
| `en` | English (fallback para qualquer chave ausente) |
| `pt-BR` | Português (Brasil) |

`GET /api/config` os lista em `locales` e o padrão em `defaultLocale`.

## Para desenvolvedores

### Dicionários por área

As mensagens ficam em `shared/i18n/messages/`, um arquivo por área do produto: `common`, `login`, `admin`, `telemetry`, `shell`, `av`, `avatar`, `editor`, `map`, `server`. Cada arquivo chama `defineMessages(area, en, ptBR)`:

```ts
// shared/i18n/messages/common.ts
import { defineMessages } from '../core';

export const common = defineMessages(
  'common',
  {
    save: 'Save',
    tooManyAttempts: 'Too many attempts. Wait a few minutes and try again.',
    errorStatus: 'Error {status}',
    'people.one': '{n} person',
    'people.other': '{n} people',
  },
  {
    save: 'Salvar',
    tooManyAttempts: 'Muitas tentativas. Aguarde alguns minutos e tente de novo.',
    errorStatus: 'Erro {status}',
    'people.one': '{n} pessoa',
    'people.other': '{n} pessoas',
  },
);
```

- `en` é a **fonte das chaves**; o tipo do segundo dicionário é derivado dele, então uma chave ausente ou extra em `pt-BR` é um **erro de compilação**. `shared/i18n/i18n.test.ts` confere a paridade de novo em tempo de teste.
- As chaves recebem o prefixo da área no momento da definição: `common.save`, `server.mail.invite.subject`, `map.validate.spawn_missing`.
- Os placeholders são `{name}` e são preenchidos por `interpolate`; um placeholder desconhecido é deixado visível de propósito para que seja corrigido.
- Plurais são duas chaves, `x.one` e `x.other`, usadas por `tn('common.people', n)`; `{n}` é injetado automaticamente.
- `shared/i18n/index.ts` junta todas as áreas em um dicionário por locale (`MESSAGES`) e exporta a API.

### Usando as mensagens

Cliente (`client/src/i18n.ts` reexporta a API compartilhada mais helpers do navegador):

```ts
import { t, tn, chooseLocale, onLocaleChange } from '../i18n';

button.textContent = t('common.save');
counter.textContent = tn('common.people', people.length);
onLocaleChange(() => render());          // redraw when the user switches
chooseLocale('pt-BR');                   // explicit choice; null = back to auto
```

`initLocale(fallback, userChoice)` roda na inicialização (e de novo quando `/api/config` chega com o padrão da instância), aplicando escolha guardada → navegador → fallback.

Servidor (`server/i18n.ts`): nunca use o `t()` global. Resolva o locale da requisição uma vez e passe um tradutor vinculado adiante:

```ts
import { localeFromRequest, translatorFor, tFor } from '../i18n';

const tr = translatorFor(localeFromRequest(req, config.defaultLocale));
sendJson(res, 404, { error: tr.t('server.http.notFound') });
// or, with an explicit locale (e-mails):
const subject = tFor(user.settings.locale ?? locale, 'server.mail.reset.subject', { appName });
```

Os handlers de rota lançam `HttpError(status, 'server.some.key')`; o `app-factory.ts` traduz a chave no idioma da requisição quando serializa o erro. Os esquemas zod usam chaves de mensagem do mesmo jeito (`z.string().min(8, 'server.auth.passwordMin')`).

Regras do [CONTRIBUTING.md](../../CONTRIBUTING.md): toda frase visível ao usuário passa pelo i18n, nos **dois** idiomas; logs e saída da CLI não são traduzidos.

### Helpers de resolução de locale

`shared/i18n/core.ts` tem as funções puras usadas nos dois lados:

- `resolveLocale(candidates, fallback)` — primeiro o casamento exato, depois por idioma base (`pt-PT` → `pt-BR`), senão o fallback.
- `localeFromAcceptLanguage(header, fallback)` — interpreta os pesos `q` e alimenta `resolveLocale`.
- `createTranslator(dicts)` — `tFor`/`tnFor`/`has`, recorrendo a `en` e, por fim, à própria chave.

### Adicionando um idioma

Exemplo: adicionando espanhol (`es`).

1. **Declare o locale.** Em `shared/branding.ts` adicione-o a `SUPPORTED_LOCALES` (`['en', 'pt-BR', 'es']`); o tipo `Locale` e `isLocale` acompanham. Em `shared/i18n/index.ts` adicione seu nome de exibição a `LOCALE_NAMES` (`es: 'Español'`).
2. **Estenda o `defineMessages`.** Hoje o helper recebe exatamente dois dicionários (`en`, `ptBR`) e o tipo `AreaMessages` é indexado por `Locale`, então o compilador vai apontar imediatamente para `shared/i18n/core.ts`: estenda `defineMessages` para aceitar o novo dicionário (mesmo conjunto de chaves de `en`) e emiti-lo sob `'es'`, e estenda `merge()`/`MESSAGES` em `index.ts` para incluir `'es'`. Mantenha a regra "as chaves de `en` são o contrato" para que traduções ausentes continuem sendo erros de compilação.
3. **Traduza todas as áreas** em `shared/i18n/messages/*.ts`, adicionando o terceiro dicionário a cada chamada. O verificador de tipos (`npm run typecheck`) e o `shared/i18n/i18n.test.ts` listam o que está faltando. Mantenha os placeholders (`{n}`, `{appName}`) e os pares de plural intactos.
4. **Confira os lugares que enumeram locales:** o seletor do login e o seletor das configurações iteram `SUPPORTED_LOCALES`, o esquema zod de `settings.locale` em `server/http/me-routes.ts` usa `z.enum(SUPPORTED_LOCALES)`, e `/api/config` lista `locales` — todos pegam o novo valor automaticamente. O comentário do `.env.example` sobre `OFFICE_DEFAULT_LOCALE` e esta página precisam de uma edição manual.
5. **Rótulos do mapa padrão** (`map.default.*`) e mensagens de validação (`map.validate.*`) fazem parte dos dicionários; traduza-os também, ou o mapa vai aparecer em inglês nas instâncias `es`.
6. **Docs** (opcional): traduza `docs/` para `docs/es/`.
7. Rode `npm run typecheck && npm test`, inicie `npm run dev`, troque o idioma na página de login e nas configurações, convide um usuário com `?lang=es` na URL de administração para ver uma prévia do e-mail nos logs, e abra um pull request.

Idiomas da direita para a esquerda não são tratados pelo layout hoje; uma contribuição RTL também precisaria de trabalho de CSS em `client/`.

### Testando traduções

- `shared/i18n/i18n.test.ts` cobre paridade, interpolação, seleção de plural e interpretação de `Accept-Language`.
- `localeFromRequest` é exercitado pelos testes de rota do servidor; adicione um caso quando adicionar um locale.
- Verificação visual: `npm run dev`, depois `http://127.0.0.1:4747/login?lang=pt-BR` e o seletor.
