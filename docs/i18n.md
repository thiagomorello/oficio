# Internationalisation (i18n)

Oficio ships in English (`en`) and Brazilian Portuguese (`pt-BR`). Every person picks their own language, the instance has a default for newcomers, and server-side texts (API errors, e-mails, the default map's labels) follow the same rules. This page explains how the language is chosen for users, how the dictionaries are organised in code, how the server decides the language of a response or an e-mail, and the exact steps to add a new language.

## For users and operators

### Where the language is chosen

| Place | What it does |
|---|---|
| **Login page** (bottom selector) | Switches the login page immediately and stores the choice in the browser (`localStorage`, key `oficio:locale`). The first option, *auto*, means "follow the browser". |
| **Settings** in the office (the gear menu, *Language*) | Same selector; additionally saves the choice in the user's profile (`PUT /api/me/settings`, field `locale`), so e-mails sent to that person use it and the choice follows them to another browser. |
| **`OFFICE_DEFAULT_LOCALE`** in `.env` | Instance default for people who have not chosen and whose browser language is unsupported, and for server messages when a request says nothing about language. |

The whole interface redraws in place when the language changes; no reload.

### Resolution order in the browser

1. The person's **explicit choice** (profile setting, or the browser-stored choice before login).
2. The **browser's languages** (`navigator.languages`), matched exactly first (`pt-BR`), then by base language (`pt-PT` → `pt-BR`, `en-GB` → `en`).
3. **`OFFICE_DEFAULT_LOCALE`**, read from `GET /api/config`.
4. If even that is invalid: `en`.

`<html lang>` is kept in sync so screen readers and spell checkers follow.

### How the server picks a language

The server handles many people at once, so it resolves a locale **per request**:

1. `?lang=<locale>` in the URL. E-mail links carry it (`/login?reset=…&lang=pt-BR`) so the login page opens in the recipient's language before any JavaScript runs.
2. The `Accept-Language` header, weighted by `q`, matched as above.
3. `OFFICE_DEFAULT_LOCALE`.

This decides the language of API error messages (`{"error": "…"}`), of the guard's plain-text refusals (`Host not allowed…`), of the `403` admin page, of the "client not built" message, and of map validation messages returned to the editor. For WebSocket connections the same resolution runs at upgrade time, with the user's saved profile language taking precedence.

**E-mails** use the recipient's saved language when the account has one (password resets, admin-triggered resets); invitations to brand-new accounts, which have no saved language yet, use the language of the admin's request. Subject, body and button labels come from the `server.mail.*` keys.

**The default map** is generated with labels in a concrete language: on first boot, room names and signs are written in `OFFICE_DEFAULT_LOCALE` and stored as data in the published map. Changing the default locale later does not rename rooms; edit them in the map editor or use *Restore default map* in the editor to regenerate the draft in the current default language. The brand sign uses the language-neutral `{brand}` label.

### Supported locales

| Code | Name shown in selectors |
|---|---|
| `en` | English (fallback for any missing key) |
| `pt-BR` | Português (Brasil) |

`GET /api/config` lists them in `locales` and the default in `defaultLocale`.

## For developers

### Dictionaries by area

Messages live in `shared/i18n/messages/`, one file per area of the product: `common`, `login`, `admin`, `telemetry`, `shell`, `av`, `avatar`, `editor`, `map`, `server`. Each file calls `defineMessages(area, en, ptBR)`:

```ts
// shared/i18n/messages/common.ts
import { defineMessages } from '../core';

export const common = defineMessages(
  'common',
  {
    save: 'Save',
    tooManyAttempts: 'Too many attempts. Wait a few minutes and try again.',
    errorStatus: 'Error {status}',
    'people.one': '{n} person',
    'people.other': '{n} people',
  },
  {
    save: 'Salvar',
    tooManyAttempts: 'Muitas tentativas. Aguarde alguns minutos e tente de novo.',
    errorStatus: 'Erro {status}',
    'people.one': '{n} pessoa',
    'people.other': '{n} pessoas',
  },
);
```

- `en` is the **source of keys**; the type of the second dictionary is derived from it, so a missing or extra key in `pt-BR` is a **compile error**. `shared/i18n/i18n.test.ts` double-checks parity at test time.
- Keys are prefixed with the area at definition time: `common.save`, `server.mail.invite.subject`, `map.validate.spawn_missing`.
- Placeholders are `{name}` and are filled by `interpolate`; an unknown placeholder is left visible on purpose so it gets fixed.
- Plurals are two keys, `x.one` and `x.other`, used through `tn('common.people', n)`; `{n}` is injected automatically.
- `shared/i18n/index.ts` merges all areas into one dictionary per locale (`MESSAGES`) and exports the API.

### Using messages

Client (`client/src/i18n.ts` re-exports the shared API plus browser helpers):

```ts
import { t, tn, chooseLocale, onLocaleChange } from '../i18n';

button.textContent = t('common.save');
counter.textContent = tn('common.people', people.length);
onLocaleChange(() => render());          // redraw when the user switches
chooseLocale('pt-BR');                   // explicit choice; null = back to auto
```

`initLocale(fallback, userChoice)` runs at boot (and again when `/api/config` arrives with the instance default), applying stored choice → browser → fallback.

Server (`server/i18n.ts`): never use the global `t()`. Resolve the request's locale once and pass a bound translator down:

```ts
import { localeFromRequest, translatorFor, tFor } from '../i18n';

const tr = translatorFor(localeFromRequest(req, config.defaultLocale));
sendJson(res, 404, { error: tr.t('server.http.notFound') });
// or, with an explicit locale (e-mails):
const subject = tFor(user.settings.locale ?? locale, 'server.mail.reset.subject', { appName });
```

Route handlers throw `HttpError(status, 'server.some.key')`; `app-factory.ts` translates the key in the request's language when it serialises the error. zod schemas use message keys the same way (`z.string().min(8, 'server.auth.passwordMin')`).

Rules from [CONTRIBUTING.md](../CONTRIBUTING.md): every user-visible sentence goes through i18n, in **both** languages; logs and CLI output are not translated.

### Locale resolution helpers

`shared/i18n/core.ts` has the pure functions used on both sides:

- `resolveLocale(candidates, fallback)` — first exact match, then base-language match (`pt-PT` → `pt-BR`), else fallback.
- `localeFromAcceptLanguage(header, fallback)` — parses `q` weights and feeds `resolveLocale`.
- `createTranslator(dicts)` — `tFor`/`tnFor`/`has`, falling back to `en` and finally to the key itself.

### Adding a language

Example: adding Spanish (`es`).

1. **Declare the locale.** In `shared/branding.ts` add it to `SUPPORTED_LOCALES` (`['en', 'pt-BR', 'es']`); the `Locale` type and `isLocale` follow. In `shared/i18n/index.ts` add its display name to `LOCALE_NAMES` (`es: 'Español'`).
2. **Extend `defineMessages`.** Today the helper takes exactly two dictionaries (`en`, `ptBR`) and the `AreaMessages` type is keyed by `Locale`, so the compiler will immediately point at `shared/i18n/core.ts`: extend `defineMessages` to accept the new dictionary (same key set as `en`) and emit it under `'es'`, and extend `merge()`/`MESSAGES` in `index.ts` to include `'es'`. Keep the "keys of `en` are the contract" rule so missing translations remain compile errors.
3. **Translate every area** in `shared/i18n/messages/*.ts`, adding the third dictionary to each call. The type checker (`npm run typecheck`) and `shared/i18n/i18n.test.ts` list what is missing. Keep placeholders (`{n}`, `{appName}`) and plural pairs intact.
4. **Check the places that enumerate locales:** the login selector and the settings selector iterate `SUPPORTED_LOCALES`, the `settings.locale` zod schema in `server/http/me-routes.ts` uses `z.enum(SUPPORTED_LOCALES)`, and `/api/config` lists `locales` — all pick the new value up automatically. The `.env.example` comment for `OFFICE_DEFAULT_LOCALE` and this page need a manual edit.
5. **Default map labels** (`map.default.*`) and validation messages (`map.validate.*`) are part of the dictionaries; translate them too, or the map will show English on `es` instances.
6. **Docs** (optional): translate `docs/` into `docs/es/`.
7. Run `npm run typecheck && npm test`, start `npm run dev`, switch the language in the login page and in settings, invite a user with `?lang=es` in the admin URL to see an e-mail preview in the logs, and open a pull request.

Right-to-left languages are not handled by the layout today; a RTL contribution would also need CSS work in `client/`.

### Testing translations

- `shared/i18n/i18n.test.ts` covers parity, interpolation, plural selection and `Accept-Language` parsing.
- `localeFromRequest` is exercised by the server route tests; add a case when you add a locale.
- Visual check: `npm run dev`, then `http://127.0.0.1:4747/login?lang=pt-BR` and the selector.
